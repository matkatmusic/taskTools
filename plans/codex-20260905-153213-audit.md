# Tackle-Tasks Pipeline Implementation Audit

Date: 2026-09-05 15:32:13 PDT  
Reviewer: Codex, with parallel Terra/Luna reviewers  
Scope: implemented changes plus the end-to-end `tackle-tasks` pipeline, especially hook-driven continuation, parallel task execution, reviews, testing, conflict repair, staging merge, and task closure.

## Executive conclusion

The implementation is not ready for global use. The high-level graph-driven design remains sound, and the core workflow/steps/hook unit tests pass, but several implementation seams violate the pipeline's correctness guarantees. The most serious defects can let a run test one filesystem state, merge a different state, and still close the task; can remove another parallel task's global mutation lock; or can strand a conforming implementation loop because the prompt permits paired tests that the commit and test machinery refuses to own.

The repository also does not currently pass its release gate: `npm test` produced one new deterministic failure in addition to a recorded baseline failure, plus two load-sensitive concurrency/acceptance failures. Several plans represented as implemented are absent or only partially implemented.

Recommendation: block global rollout until the Critical and High findings below are fixed and exercised by same-repository, multi-task acceptance tests.

## Critical findings

### C1. The final file fence ignores every uncommitted change; the resume fence ignores untracked files

Evidence:

- `scripts/tackle-tasks/shared/checkTaskFileFence.ts:84-101` computes changes solely with `git diff --name-only <base>...HEAD`. It never examines the index, tracked working-tree changes, or untracked files.
- `scripts/tackle-tasks/shared/checkResumedWorktreeFence.ts:42-49` adds `git diff --name-only HEAD`, which covers staged and unstaged tracked changes but still omits untracked files.
- `scripts/tackle-tasks/shared/commitTaskWork.ts:30-51` intentionally stages only declared owned paths.

Failure mode: an agent can create or modify an out-of-fence file, and the full suite can pass using that dirty file. The final fence reports `inside: true`; the selective commit excludes the file; the staging merge therefore contains a different state than the state tested; cleanup can then delete the only copy. The pipeline can archive success and close the task although staging is broken or incomplete.

Required amendment:

1. Build one canonical changed-path collector used by resume fencing, final fencing, committing, and task-test discovery.
2. Include committed, staged, unstaged, and untracked paths in every occurrence/submodule.
3. Run the decisive suite only after proving the worktree is clean except for explicitly exempt pipeline bookkeeping.
4. Re-run or verify the fence after automatic commits and immediately before merge.
5. Add acceptance cases for untracked and tracked-uncommitted out-of-fence files, including files whose presence makes tests pass.

### C2. Prompt ownership, commit ownership, fence ownership, and test discovery disagree about paired test files

Evidence:

- The implementation prompt explicitly permits a test file paired with each owned source file even when that test path is not separately declared.
- `preparedTask.ts` derives paired-test paths by convention.
- `scripts/tackle-tasks/shared/commitTaskWork.ts:71-75` derives commit ownership only from `modifiableFiles(task)`.
- The fences likewise use declared/modifiable files only.
- `scripts/tackle-tasks/shared/runTaskTestsImpl.ts:103-118` discovers test files from committed diffs, so an allowed-but-unstaged paired test is invisible.

Failure mode: a conforming implementer creates the paired test authorized by its prompt. The commit step leaves it untracked, test discovery reports that no test was added, and the repair loop cannot converge because subsequent commits continue to exclude the file.

Required amendment: define one ownership manifest per task, including declared implementation paths, derived paired-test paths, approved plan/checkpoint artifacts, and recursively owned submodule occurrences. Persist it in the task packet and consume it everywhere. Add an end-to-end test where only the source path is declared and the paired test is newly created; do not let the scripted agent perform its own broad `git add`/commit in that test.

### C3. Reset can delete another task's global source lock and mutation guard, then overwrite concurrent task-state changes

Evidence:

- `scripts/tackle-tasks/resetTask.ts:68-78` removes the target worktree/lease and then unconditionally removes `.git/taskTools-source.lock` and `.mutation-guard`, without checking their recorded owner.
- `scripts/tackle-tasks/resetTask.ts:111-125` writes task and completed-task state directly, without `withTaskStateLock` and without atomic replacement.

Failure mode: while task B holds the source lock during merge, reset of task A can remove B's lock and guard. Task C can then enter the same source mutation region. B's eventual cleanup can remove C's replacement guard. Concurrent git mutations and lost `tasks.json` updates become possible—the exact class of corruption the parallel pipeline is supposed to prevent.

Required amendment:

1. Parse and compare lock ownership before removal; only the owning `(runId, taskNumber)` may release it.
2. Make release compare-and-delete safe against owner replacement.
3. Perform all task-state reads/modifications/writes under `withTaskStateLock`, using atomic temp-file publication.
4. Add a three-run acceptance test: B holds the merge lock, A resets, C attempts entry; C must remain excluded and B's guard must remain owned.

## High findings

### H1. Real packet-file continuation bypasses the pipeline's structured failure handling

`scripts/runStepHook.ts:39-54` resolves the wrapper packet with a raw `readFileSync` plus `JSON.parse` before the normal graph walker can classify missing, empty, or malformed configuration. An empty packet without the test-only `RUN_STEP_CONFIG` override reaches the top-level `uncaughtException` path. That path may log against a default/unrelated run identity and overwrites rather than appends the existing run log.

Required amendment: move packet resolution inside the same expected-failure boundary as graph walking; validate packet schema and identity before use; return a stable blocking decision with the actual packet path and task/run identity; append exception diagnostics without destroying prior log history. Add hook-process tests that use real packet files and do not set `RUN_STEP_CONFIG`.

### H2. Live plan mode is not guarded at the mutating hook boundary

The planned plan-mode hook is absent, it is not registered in `hooks/hooks.json`, and the `/resetTask` branch in `runStepHook.ts` invokes mutation without checking the current hook payload's `permission_mode`. `PREFLIGHT_OK_Q` checks static settings later and cannot protect reset, which occurs before preflight; static default mode can also differ from the live session mode.

Required amendment: every independently invokable mutation hook must reject live `permission_mode === "plan"` before filesystem or git mutation. Register and test the guard for `/runStep`, `/resetTask`, and any direct mutation entrypoint.

### H3. The required disk-space preflight was replaced by a materially different check

The planned `IS_DISK_SPACE_SUFFICIENT_Q` implementation and route are absent. `PREFLIGHT_OK_Q` checks a 5 GB threshold on `projectRoot`, rather than the specified threshold on the filesystem that will contain the eventual worktree (or its nearest existing ancestor), and folds the result into a generic preflight failure.

Required amendment: implement the dedicated block with deterministic output and routing, probe the actual destination volume, keep the task inactive on failure, and test low-space routing without relying on the host's real disk state.

### H4. Reset-generated per-task `steps.json` loses canonical `mutating` metadata

When task config is missing, `resetTask.ts` calls `generateSteps` directly. `generateSteps.ts` preserves mutating flags only from an existing output file; with no file, the generated steps have no such flags. The skill emitter seeds canonical metadata first, so the two generation paths produce different contracts.

Required amendment: make the diagram plus a canonical metadata source the sole generation input. Both initial/reset and normal initialization must call the same pair generator. Test a fresh task directory and assert every mutating block retains its flag.

### H5. Per-task workflow and steps publication is neither locked nor atomic as a pair

Initial concurrent launches can both observe an inactive task and regenerate. Workflow publication uses a temporary file, but steps publication uses a direct `writeFileSync`; there is no per-task generation lock or pair-level version/checksum. The hook can observe a new workflow with old/truncated steps or vice versa.

Required amendment: serialize generation per task, generate both artifacts into unique temporary files, validate their cross-references, and publish under one versioned manifest/commit point. Readers must reject mismatched versions. Add a concurrent-initialization stress test.

### H6. Conflict repair rejects valid deletion resolutions and does not validate the receipt against Git's unresolved state

`COMMIT_MERGE_CONFLICT_FIX_IF_NEEDED.ts` reads every conflicted path after a claimed resolution. A valid modify/delete resolution that removes a file therefore throws `ENOENT`. The code only shape-checks the receipt, does not require `unresolvedPaths` to be empty when `resolved` is true, and does not query `git diff --diff-filter=U`; marker-free binary conflicts can be misclassified until commit fails.

Required amendment: treat deletion as a valid resolution; validate all receipt fields; use Git's unmerged index as the source of truth; compare it to the receipt; route remaining conflicts back to the repair prompt rather than hard-failing. Add modify/delete, rename, and binary conflict acceptance tests.

### H7. Task-test execution discovers submodule tests but never runs their suites

`scripts/tackle-tasks/shared/runTaskTestsImpl.ts:101-118` builds `relativeTestFilesByOccurrenceId`, but the map is unused. Lines 133-136 explicitly run only the top-level worktree suite. A changed test in a submodule can appear in the result's `testFiles` while never being executed during task-test review.

Required amendment: execute the appropriate test command in every occurrence containing changed tests, aggregate timeout/failure evidence with occurrence-qualified identities, and send that evidence to the reviewer. Restore an active test that proves a failing nested-suite test makes this block fail.

### H8. Timeout cleanup can crash the runner instead of returning a diagnostic result

In `taskTestsRunner.ts`, the timer callback suppresses `ESRCH` but throws any other process-group kill error from the asynchronous callback. That becomes an uncaught process exception rather than the promised structured timed-out result. If no PID exists at timeout, the callback returns without itself settling the run.

Required amendment: never throw from the timer callback; record kill diagnostics, settle once, and preserve stdout/stderr. Cover missing PID, permission error, already-exited process group, and child `error`/`close` races with injected process controls.

### H9. Detached Codex planning/review subprocesses are not safely resumable

The difficult-task Codex planner uses fixed prompt/output/PID/done paths and spawns on every entry. Prompt-producing steps are not checkpointed by the hook, so a kill/retry can spawn multiple detached processes writing the same files. Generated shell uses unquoted paths, so project roots containing spaces can fail. The wait path has no total deadline. Claude CLI fallbacks used by review subprocesses also lack equivalent timeouts.

Required amendment: create an owner-stamped subprocess record, reuse a live matching process, reject/retire stale owners safely, quote all argv by using `spawn`/`execFile` rather than generated shell, use unique temp outputs plus atomic publication, and enforce a total deadline on every primary and fallback agent command.

### H10. The task-state lock can permanently strand automation after abrupt termination

`scripts/taskStateLock.ts` uses exclusive creation but deliberately provides no stale-owner recovery. A SIGKILL during any of the many task-state critical sections leaves the repository globally blocked until manual deletion.

Required amendment: store PID, process start identity, hostname, run ID, and acquisition time; reclaim only after proving the owner is dead/stale; use a lease refresh for long sections; make unlock owner-checked. Test SIGKILL recovery and PID reuse.

### H11. Three planned safety deliverables are absent, and several others are only partial

At minimum:

- The dedicated disk-space gate is absent.
- The live/plan-mode mutation guard is absent.
- The planned task-specific pipeline health-check script is absent; the older generic shell health check does not satisfy the required task/run ownership and orphan detection behavior.
- Reset config regeneration, generation serialization, conflict receipts, and timeout process handling are partial implementations of their plan requirements.

Required amendment: maintain a plan-to-code verification matrix containing the intended file, exported entrypoint, route, tests, and acceptance scenario. Do not mark the implementation batch complete merely because adjacent behavior exists.

## Medium findings and proof gaps

### M1. Acceptance tests do not prove same-repository parallel execution

The concurrent acceptance scenario runs equivalent work in two separate repositories. It therefore does not exercise contention over one repository's task-state file, source lock, staging branch, worktree leases, or mutation guard. The happy path uses a low-difficulty task and skips plan/test review; scripted implementation also stages and commits directly, bypassing the pipeline's selective auto-commit seam. No acceptance path drives the implementation-test repair loop or full-suite repair loop end to end.

Required amendment: run at least two different tasks concurrently in one source repository. Force interleaving at lock boundaries; make one task require plan revision, one require test repair, and one encounter a staging conflict. Assert serial source mutation, preserved task-state updates, correct resumability, and eventual closure of each task.

### M2. Review bypasses conflict with the stated universal-review premise

Low-difficulty tasks intentionally skip plan review and task-test review. Separately, a resumed `plan-scrapped` checkpoint can instruct the reviewer to approve by default instead of judging the revised plan. If the product requirement is that tasks receive independent plan review, this is a design discrepancy, not merely missing coverage.

Required amendment: either document the explicit risk-based exception in the high-level contract or remove the bypass. A previously scrapped plan must be substantively re-reviewed after revision.

### M3. Diagram documentation is stale

The monolith diagram still describes shared workflow/config behavior even though active runs use per-task artifacts. Hook timeout comments and configured timeout also disagree. Stale executable-adjacent documentation increases the chance of repairing the wrong lifecycle.

Required amendment: generate or validate architectural annotations from the same per-task contract, and add a docs/diagram consistency check for artifact locations, block names, and timeout values.

## Release criteria

Before rollout, require all of the following:

1. Fix C1-C3 and H1-H10, with fault-injection tests at each durability boundary.
2. Implement or explicitly reject each absent plan deliverable; update the task records accordingly.
3. Make raw `npm test` deterministic and green except for an explicitly accepted, reviewed baseline; the new reflow failure cannot enter that baseline as a substitute for implementation.
4. Add same-repository parallel acceptance covering plan revision, auto-commit, task-test repair, full-suite repair, merge conflict resolution including deletion/binary cases, staging merge, and atomic task closure.
5. Prove that the exact commit merged to staging—not a dirty precursor state—is the commit whose task tests and full suite passed.
6. Run acceptance repeatedly under parallel/full-suite load and with paths containing spaces.

## What appears sound

The graph-driven continuation model and per-task artifact direction are worth retaining. Core diagram generation and hook traversal have substantial unit coverage and currently pass their focused suites. The new ownership locks, leases, receipts, and checkpoint concepts are also directionally correct. The failures above are mostly cross-component contract mismatches and crash/concurrency edges, not evidence that the overall pipeline architecture must be replaced.
