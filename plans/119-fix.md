# Task 119 fix recommendation

## Verdict

The staged revert is caused by `publishCanonicalRef` advancing a branch that is checked out in the canonical repository with `git update-ref`:

```text
git -C <canonical checkout> update-ref <base ref> <target OID> <recorded base OID>
```

`update-ref` changes only the branch ref. Because `HEAD` is a symbolic reference to that branch, `HEAD` immediately resolves to the new integration commit, but the real index and working tree remain at the recorded base. Git then compares the old index to the new `HEAD` and renders that stale state as a staged revert of the merge. No successful-path command actively writes the old files back.

The previously suspected writers are not responsible for the observed successful `--run` path:

- `runFinalizer.ts` receives `approvedOwnFileChanges: []` from `mergePipeline.ts`, so its real-index `git add` loop does not execute.
- The main-checkout `git checkout` calls in `mergeTaskWorktrees.ts` belong to the older `--merge` path, not the `--run` path used by `runMergePhase.ts`.
- `recoveryRefs.ts` passes `GIT_INDEX_FILE` to both `git add -A` and `git write-tree`, so it operates on its scratch index.
- `repositoryIntegration.ts` also isolates `read-tree` and `update-index` behind a scratch `GIT_INDEX_FILE`.

The existing `basePublication.test.ts` fixture does not expose the bug: it publishes `refs/heads/base` while `main` is checked out. Coverage must publish the ref to which `HEAD` is actually attached.

## Do not use `reset --keep` after `update-ref`

This proposed sequence is insufficient:

```text
git update-ref <checked-out ref> <target> <old>
git reset --keep <target>
```

At the time of the reset, `HEAD` already equals `<target>`. `reset --keep` therefore treats the stale pre-merge files as local edits relative to the target and preserves them. In a reproduction where the target added `merged.txt`, the status changed as follows:

```text
after update-ref:          D  merged.txt
after reset --keep target:  D merged.txt
```

The reset refreshed the index and merely converted the staged deletion into an unstaged deletion. The merged file was still absent from disk, so tests would still run against stale code.

## Recommended primitive

Keep the compare-and-swap `update-ref`, but refresh each affected checkout with an explicit old-tree-to-new-tree transition:

```text
git read-tree --no-recurse-submodules -u -m <recorded base OID> <target OID>
```

The two explicit tree arguments retain the information that `reset --keep` loses after the ref move. In empirical checks this command:

- installed files added or modified by the target commit;
- updated the real index to the target tree;
- preserved unrelated staged local changes;
- preserved unrelated unstaged local changes; and
- refused to overwrite an overlapping local modification.

Use `--no-recurse-submodules` so refreshing a parent checkout cannot implicitly reset a nested checkout. Each logical repository is published independently, and a detached nested checkout must remain untouched.

## Transactional publication design

Implement checkout refresh as a publication phase in `publishBases`, rather than as an untracked side effect inside `publishCanonicalRef`. Whole-run rollback currently covers refs, so the checkout transitions must participate in the same transaction.

### Types and result reporting

Add these types beside `UpdatedRef` and `RollbackOutcome`, and extend `PublicationResult` so a failed checkout reversal cannot be hidden behind a successful ref rollback:

```ts
export type CheckoutTransition = {
    repoName: string;
    occurrencePath: string;
    refName: string;
    oldOid: string;
    newOid: string;
};

export type CheckoutRollbackOutcome = {
    transition: CheckoutTransition;
    rolledBack: boolean;
    recoveryCommand: string;
};

export type PublicationResult = {
    published: boolean;
    rollback: RollbackOutcome[];
    checkoutRollback: CheckoutRollbackOutcome[];
};
```

Build a transition only when all of the following hold:

1. `git symbolic-ref --quiet HEAD` succeeds in the canonical occurrence.
2. Its trimmed output exactly equals `repo.canonicalRefName`.
3. The existing publication revalidation confirms that ref still resolves to `repo.recordedBaseOid`.

A detached `HEAD` or a checkout of a different branch therefore produces no transition. Updating an unassociated ref must not touch that checkout's index or files.

Add these helpers after `revalidateApprovalInputs`. `checkedOutTransition` performs the exact symbolic-ref guard. `runCheckoutTransition` is shared by preflight, forward application, and reversal so those paths cannot drift into using different Git commands.

```ts
function checkedOutTransition(repo: PublicationTarget): CheckoutTransition | null {
    const head = runGit(repo.canonicalOccurrencePath, ["symbolic-ref", "--quiet", "HEAD"]);
    if (!head.ok || head.stdout.trim() !== repo.canonicalRefName) return null;
    return {
        repoName: repo.name,
        occurrencePath: repo.canonicalOccurrencePath,
        refName: repo.canonicalRefName,
        oldOid: repo.recordedBaseOid,
        newOid: repo.targetOid,
    };
}

function runCheckoutTransition(
    transition: CheckoutTransition,
    oldOid: string,
    newOid: string,
    dryRun: boolean,
): boolean {
    const args = ["read-tree", "--no-recurse-submodules"];
    if (dryRun) args.push("-n");
    args.push("-u", "-m", oldOid, newOid);
    return runGit(transition.occurrencePath, args).ok;
}

function preflightCheckoutTransition(transition: CheckoutTransition): boolean {
    return runCheckoutTransition(transition, transition.oldOid, transition.newOid, true);
}

function applyCheckoutTransition(transition: CheckoutTransition): boolean {
    return runCheckoutTransition(transition, transition.oldOid, transition.newOid, false);
}

function formatCheckoutRecoveryCommand(transition: CheckoutTransition): string {
    return `git -C ${transition.occurrencePath} read-tree --no-recurse-submodules -u -m ${transition.newOid} ${transition.oldOid}`;
}

function rollbackCheckoutTransitions(applied: CheckoutTransition[]): CheckoutRollbackOutcome[] {
    return [...applied].reverse().map((transition) => ({
        transition,
        rolledBack: runCheckoutTransition(transition, transition.newOid, transition.oldOid, false),
        recoveryCommand: formatCheckoutRecoveryCommand(transition),
    }));
}
```

### Phase 1: preflight every checkout transition

Before moving any ref, run the dry form for every transition:

```text
git read-tree --no-recurse-submodules -n -u -m <old> <new>
```

If any preflight fails, return `published: false` without moving any ref. This safely handles cases such as:

- a tracked local edit overlapping a merged change;
- an untracked file that the target commit would create;
- an unusable or locked real index; or
- another condition that prevents updating the checkout.

Unrelated local changes should pass preflight and remain preserved.

The corresponding beginning of `publishBases`, including the existing three authorization/revalidation gates, should be:

```ts
export function publishBases(
    repos: PublicationTarget[],
    approvalState: RunState,
    rootIntegration: { repoPath: string; refName: string },
): PublicationResult {
    const notPublished = (): PublicationResult => ({
        published: false,
        rollback: [],
        checkoutRollback: [],
    });

    if (!checkRootIntegrationOidExists(rootIntegration.repoPath, rootIntegration.refName)) {
        return notPublished();
    }
    if (!revalidateApprovalInputs(approvalState)) {
        return notPublished();
    }
    if (!revalidateRecordedBaseOids(repos).ok) {
        return notPublished();
    }

    const checkoutTransitions = repos.flatMap((repo) => {
        const transition = checkedOutTransition(repo);
        return transition === null ? [] : [transition];
    });
    if (!checkoutTransitions.every(preflightCheckoutTransition)) {
        return notPublished();
    }
```

### Phase 2: publish refs using the existing CAS behavior

Run the existing canonical `update-ref <ref> <new> <old>` operations and other-occurrence fast-forwards. If this phase fails, use the existing ref rollback. No checkout transition has been applied yet, so the index and working tree remain in their original state.

Continue `publishBases` with the existing ref-publication loop. The only structural change is that ref failure returns immediately before any real checkout has been transitioned:

```ts
    const updatedSoFar: UpdatedRef[] = [];
    for (const repo of repos) {
        const canonicalResult = publishCanonicalRef(repo);
        if (!canonicalResult.ok) {
            return {
                published: false,
                rollback: rollbackUpdatedRefs(updatedSoFar),
                checkoutRollback: [],
            };
        }
        updatedSoFar.push(canonicalResult.updated!);

        const fastForwardResult = fastForwardOtherOccurrences(repo);
        updatedSoFar.push(...fastForwardResult.updated);
        if (!fastForwardResult.ok) {
            return {
                published: false,
                rollback: rollbackUpdatedRefs(updatedSoFar),
                checkoutRollback: [],
            };
        }
    }
```

### Phase 3: apply checked-out transitions

Only after every ref has published successfully, apply each preflighted transition:

```text
git read-tree --no-recurse-submodules -u -m <old> <new>
```

Track which transitions completed. Return `published: true` only after all required transitions have succeeded.

Preflight substantially narrows the failure window, but it does not eliminate races: a user or process could modify a file between preflight and application. An application failure must therefore be treated as publication failure, not ignored.

Continue `publishBases` by applying each checkout transition and recording it only after `read-tree` succeeds:

```ts
    const appliedTransitions: CheckoutTransition[] = [];
    for (const transition of checkoutTransitions) {
        if (!applyCheckoutTransition(transition)) {
            const checkoutRollback = rollbackCheckoutTransitions(appliedTransitions);
            const rollback = rollbackUpdatedRefs(updatedSoFar);
            return { published: false, rollback, checkoutRollback };
        }
        appliedTransitions.push(transition);
    }

    return { published: true, rollback: [], checkoutRollback: [] };
}
```

This final brace completes the `publishBases` function begun in Phase 1.

### Phase 4: rollback after an application failure

If a checkout transition unexpectedly fails:

1. Reverse each already-applied transition in reverse order with:

   ```text
   git read-tree --no-recurse-submodules -u -m <new> <old>
   ```

2. Roll published refs back with the existing `<new> -> <old>` CAS operations.
3. Report failures for both checkout rollback and ref rollback, with exact recovery commands, instead of claiming that the whole run rolled back cleanly.

The Phase 3 failure branch above deliberately invokes `rollbackCheckoutTransitions` before `rollbackUpdatedRefs`. While the published refs still resolve to the new commits, the reverse `read-tree <new> <old>` transitions have the same coherent starting point as their forward transitions. Ref rollback then makes `HEAD`, the restored index, and restored files agree on the old commit again.

Only transitions pushed into `appliedTransitions` are reversed. A failed `read-tree` is expected to leave its index transaction unapplied; attempting `<new> <old>` on that failed transition could itself overwrite or reject the still-old state. Preflight makes this case a race/error path rather than normal conflict handling.

The distinct `checkoutRollback` result remains necessary even though the code attempts both rollback layers. Merely reporting the ref outcomes would allow a failed checkout reversal to leave the opposite mismatch: an old `HEAD` with a target-era index and working tree.

## Suggested implementation boundaries

The production change should remain concentrated in `scripts/basePublication.ts`:

- add a helper that detects whether a publication ref is checked out and constructs a `CheckoutTransition`;
- add preflight/apply/reverse helpers that invoke `read-tree`;
- extend `publishBases` into the concrete phases above; and
- extend rollback reporting to cover failed checkout reversal where necessary.

Add behavioral coverage in `tests/basePublication.test.ts`. No change is required in the merge/consolidation machinery to produce the target commit; that machinery is already producing the correct commit and publication target.

## Concrete regression test

Add `existsSync` and `readFileSync` to the existing `node:fs` import in `tests/basePublication.test.ts`:

```ts
import { existsSync, mkdtempSync, readFileSync, writeFileSync } from "node:fs";
```

Then add this test after `test_compareAndSwapPreventsClobberingConcurrentUpdate`:

```ts
test("test_publishingCheckedOutCanonicalRefRefreshesRealIndexAndWorkingTree", () => {
    const canonicalPath = makeRepo();
    const recordedBaseOid = commitFile(canonicalPath, "tracked.txt", "before");
    writeFileSync(join(canonicalPath, "tracked.txt"), "after");
    writeFileSync(join(canonicalPath, "merged.txt"), "merged");
    git(canonicalPath, "add", "-A");
    git(canonicalPath, "commit", "-q", "-m", "target");
    const targetOid = git(canonicalPath, "rev-parse", "HEAD");

    // Recreate the state immediately before publication: the checked-out branch,
    // real index, and working tree all contain the recorded base, while targetOid
    // is an already-prepared commit that publication will install with update-ref.
    git(canonicalPath, "reset", "--hard", recordedBaseOid);
    const repo: PublicationTarget = {
        name: "checked-out-canonical",
        canonicalOccurrencePath: canonicalPath,
        canonicalRefName: "refs/heads/main",
        otherOccurrences: [],
        recordedBaseOid,
        targetOid,
    };

    const result = publishBases([repo], approvedRunState(), makeRootIntegration(true));

    assert.equal(result.published, true);
    assert.equal(git(canonicalPath, "rev-parse", "HEAD"), targetOid);
    assert.equal(git(canonicalPath, "write-tree"), git(canonicalPath, "rev-parse", `${targetOid}^{tree}`));
    assert.equal(existsSync(join(canonicalPath, "merged.txt")), true);
    assert.equal(readFileSync(join(canonicalPath, "merged.txt"), "utf8"), "merged");
    assert.equal(readFileSync(join(canonicalPath, "tracked.txt"), "utf8"), "after");
    assert.equal(git(canonicalPath, "status", "--short"), "");
});
```

This test fails on the current implementation at the index-tree assertion because `HEAD` advances while the real index remains at `recordedBaseOid`. It also rejects the insufficient post-publication `reset --keep` approach: that approach can make the index match the target, but `merged.txt` remains absent and `tracked.txt` remains stale in the working tree.

## Required regression cases

1. **Checked-out canonical ref, clean checkout**
   - Publish the branch referenced by `HEAD`.
   - Assert `HEAD`, the index tree, and working-tree contents all match `targetOid`.
   - Assert `git status --porcelain` is empty.

2. **Target adds a file**
   - Assert the file exists on disk after publication.
   - Assert it is not reported as a staged or unstaged deletion.

3. **Unrelated unstaged local edit**
   - Modify a tracked path that is unchanged between old and new trees.
   - Assert the local bytes survive and retain their unstaged status while merged paths advance.

4. **Unrelated staged local edit**
   - Stage a change to a path unchanged between old and new trees.
   - Assert the staged blob and staged status survive while merged paths advance.

5. **Unrelated untracked file**
   - Assert it remains untracked and byte-identical after publication.

6. **Overlapping tracked edit**
   - Locally modify a path also changed by the target.
   - Assert preflight blocks publication and the ref, index, and working tree remain at their pre-publication state.

7. **Untracked overwrite collision**
   - Create an untracked path that the target adds.
   - Assert preflight blocks publication without deleting or staging the untracked file.

8. **Detached `HEAD`**
   - Publish the named ref while the canonical checkout is detached.
   - Assert the ref advances but detached `HEAD`, the real index, and files remain untouched.

9. **Different checked-out branch**
   - Publish a ref other than the branch referenced by `HEAD`.
   - Assert no checkout transition occurs.

10. **Later ref-publication failure**
    - Allow an earlier ref to publish, then force a later CAS/fast-forward failure.
    - Assert refs roll back and no checkout was transitioned because application occurs only after all ref moves succeed.

11. **Checkout-application failure after preflight**
    - Inject a failure or race after refs publish and after at least one transition applies.
    - Assert applied checkouts reverse, refs roll back, and any incomplete rollback is reported rather than hidden.

12. **Parent and nested repository**
    - Assert parent refresh updates its gitlink entry without recursively resetting a detached or separately managed nested checkout.

## Acceptance condition

After a successful merge publication, every canonical occurrence whose published ref is its checked-out branch must satisfy:

```text
HEAD == targetOid
index contains targetOid's published tree plus only pre-existing staged local changes
working tree contains the published files plus only pre-existing local changes
```

The publication must abort safely when those states cannot be established without overwriting a real local change. A successful result must never leave the just-published commit visible only through `git show HEAD` while the index and files still contain the recorded base.
