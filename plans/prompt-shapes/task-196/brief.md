# Task 196: Run the full suite on the fresh worktree in the preamble and exit staging-suite-red when staging is red

## Goal

**This task is considered done when all of these are true:**

- A worktree for task N spawned from staging (where staging is aligned with HEAD and HEAD's test suite fails to pass) is created but the workflow exits before document generation occurs and reports that the test suite is failing.
- A worktree for task N spawned from staging (where staging is aligned with HEAD and HEAD's test suite is passing) is created and the workflow makes it past the 'run the full suite before generating docs' step.
- No new code related to moving staging to HEAD is created.

## Not in scope

- Changing which files FIX_THE_CODEBASE_FOR_SUITE may edit; that block keeps its owned-files fence.
- Moving knownFailingTests.json or changing where the baseline is read from.
- Changing how staging is moved; ensureStagingWorktree, CREATE_WORKTREE, and REBASE_RESUMED_WORKTREE_ONTO_STAGING stay as they are.

## problemSolvedByTask

a failing test suite that existing on the branch that 'staging' and the worktree were cut from prevents the workflow from getting past the 'run the test suite' block, blocking the entire run from completing, because the workflow agents can't touch the files causing the failing tests, because those files are not in the task's modifiableFiles list.

## User request

Run the full suite on the fresh task worktree in the preamble, and stop the run when staging itself is red.

Order of operations for /tackle-tasks N:
1. The existing preamble blocks run as today: PREAMBLE_STATUS_CHECK, IS_TASK_BLOCKED_Q, IS_TASK_ACTIVE_Q, PREFLIGHT_OK_Q, MARK_TASK_ACTIVE.
2. The existing staging code moves staging to the source branch tip: ensureStagingWorktree in scripts/tackle-tasks/shared/stagingWorktree.ts; CREATE_WORKTREE cuts the task worktree from staging; REBASE_RESUMED_WORKTREE_ONTO_STAGING catches a resumed worktree up. Reuse that code; add no new git operations for staging.
3. NEW: right after the worktree exists and holds the lease and submodules (after INIT_SUBMODULES_RECURSIVELY, before DOCUMENT_GENERATION), a new mutating block RUN_SUITE_ON_FRESH_WORKTREE runs the full suite inside the task worktree, using the same code RUN_FULL_SUITE uses (scripts/tackle-tasks/shared/runFullSuite.ts, with the knownFailingTests.json baseline from the project root).
4. NEW: a decision block DOES_FRESH_WORKTREE_SUITE_PASS_Q. YES: continue to DOCUMENT_GENERATION and the rest of the pipeline. NO: exit through REPORT_ONLY_EXIT with a new exit type `staging-suite-red` and an exit note that says the suite fails on staging before the task changed anything, lists the new failing tests, and says the suite needs fixing first before the task can run. The worktree is preserved. The task is marked inactive and the lease released, the same way the other report-only exits do it.
5. On a resumed worktree that already carries task commits, the suite is not run by these new blocks; that case keeps today's path.

Why: task 36 ran to suite-red after IMPLEMENT_TASK because a test that was already red on staging (tests/stage-and-summarize-stop.test.ts) is outside the task's owned files, so FIX_THE_CODEBASE_FOR_SUITE correctly refused to touch it. The run spent two plan rounds, two reviews, an implementation, and two fix attempts before finding out. The check belongs at the start.

## Clarification answer (2026-09-07)

Do not edit `scripts/tackle-tasks/preambleStatusCheck/INIT_SUBMODULES_RECURSIVELY.ts` or its template. Use a new decision block instead.

The packet already carries `docsMode` when it reaches INIT_SUBMODULES_RECURSIVELY (field declared in `scripts/tackle-tasks/preambleStatusCheck/_packet.ts`). `TAKE_WORKTREE_LEASE.ts` and `RESET_WORKTREE.ts` set it to `AUTOGEN` (fresh or reset worktree). `DOES_FENCE_COVER_WORKTREE_Q.ts` sets it to `UPDATE` (resumed worktree with task commits). That value is the fresh-vs-resumed signal.

Routing:
- In `diagrams/tackle-tasks/pipeline-preambleStatusCheck.mmd`, change the edge `INIT_SUBMODULES_RECURSIVELY --> DOCUMENT_GENERATION` to `INIT_SUBMODULES_RECURSIVELY --> IS_WORKTREE_FRESH_Q`.
- New decision block `IS_WORKTREE_FRESH_Q` (shape of `DOES_WORKTREE_EXIST_Q.ts`: strip `next`, return `{...packet, box, scriptSignal: CONTINUE, next}`). `docsMode === "AUTOGEN"` -> `next: "RUN_SUITE_ON_FRESH_WORKTREE"`. `docsMode === "UPDATE"` -> `next: "DOCUMENT_GENERATION"`. Any other value: throw, the same way `DOCUMENT_GENERATION.ts` throws on an unknown docs mode.
- `RUN_SUITE_ON_FRESH_WORKTREE --> DOES_FRESH_WORKTREE_SUITE_PASS_Q`; YES -> `DOCUMENT_GENERATION`, NO -> report-only exit `staging-suite-red`, as the task already says.

The three IS_WORKTREE_FRESH_Q files are added to this task's owned files.

## Clarification answer (2026-09-07)

Do not add `scripts/tackle-tasks/generateSteps.ts`. It must not change.

The mutating flag is hand-written by design. `scripts/tackle-tasks/generateSteps.ts` line 182 says: "The mutating flag is hand-written, so regenerating from the arrows must not drop it." `getMutatingFromPreviousConfig` reads the flag from the existing `scripts/tackle-tasks/diagram-steps.json` and carries it forward; the generator never derives it from a template or script. Every existing mutating block (CREATE_WORKTREE, RESET_WORKTREE, RUN_FULL_SUITE, and the rest) got its flag that way.

Procedure for the new block:
1. Run the generator so `scripts/tackle-tasks/diagram-steps.json` gains the new entries.
2. Add `"mutating": true` to the `RUN_SUITE_ON_FRESH_WORKTREE` entry in `scripts/tackle-tasks/diagram-steps.json` by hand. The task owns that file. This is the one field in that file that is meant to be hand-edited.
3. Run the generator again and confirm the flag survives. That confirms step 2 is correct.

`IS_WORKTREE_FRESH_Q` and `DOES_FRESH_WORKTREE_SUITE_PASS_Q` are decisions and get no flag.
