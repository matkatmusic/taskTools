# Plan: task 61 — move the owned-file existence check after submodule init

## Behavior in plain English

Today PREFLIGHT_OK_Q asks git, in the parent repo, whether each modifiableFiles entry exists in the base tree. A file inside a submodule is not in the parent tree. Git sees only a gitlink. So preflight says the file is missing, and the run exits before a worktree exists.

After this change PREFLIGHT_OK_Q no longer checks files. INIT_SUBMODULES_RECURSIVELY checks them instead. It runs after the worktree exists and after submodules are populated. It looks on disk in the worktree. A file inside a submodule is on disk by then. A file that is truly missing, and not in createsFiles, routes the run to FAILURES_EXIT with exitType "owned-file-missing". FAILURES_EXIT is the exit every post-worktree failure already uses.

## Step 3 — GREEN: INIT_SUBMODULES_RECURSIVELY.ts

Replace the body of `main` with this shape. Keep the existing imports and add the four new ones shown.

```ts
import { existsSync, realpathSync } from "node:fs";
import { join } from "node:path";
import { fileURLToPath } from "node:url";
import { SCRIPT_SIGNAL } from "../../shared/contracts.ts";
import { modifiableFiles } from "../../shared/prepareTasks.ts";
import { readTaskFile, resolveTaskFiles } from "../../shared/taskFiles.ts";
import { initTaskSubmodules } from "../shared/initTaskSubmodules.ts";
import type { EntryPacket } from "./_packet.ts";

export function main(input: string): EntryPacket & { next: string } {
    const { next: _next, ...packet } = JSON.parse(input) as EntryPacket & { next?: string };
    initTaskSubmodules({
        worktreePath: packet.worktree, taskNumber: packet.taskNumber, runId: packet.runId,
        projectRoot: packet.projectRoot, stepId: "init-submodules",
    });
    // Submodules are populated now, so a file inside one is on disk; preflight could not see it in the parent tree.
    const task = readTaskFile(resolveTaskFiles(packet.projectRoot).tasksPath).find((entry) => entry.taskNumber === packet.taskNumber);
    if (task === undefined) throw new Error(`task ${packet.taskNumber} not found in tasks.json`);
    const createsFiles: string[] = Array.isArray((task as any).createsFiles) ? (task as any).createsFiles : [];
    const missingFiles = modifiableFiles(task).filter((file) => !createsFiles.includes(file) && !existsSync(join(packet.worktree, file)));
    if (missingFiles.length > 0) {
        return {
            ...packet,
            box: "INIT_SUBMODULES_RECURSIVELY",
            scriptSignal: SCRIPT_SIGNAL.CONTINUE,
            exitType: "owned-file-missing",
            exitNote: `task ${packet.taskNumber}: modifiableFiles names ${missingFiles.join(", ")} but ${missingFiles.length === 1 ? "that file is" : "those files are"} not in the worktree at ${packet.worktree}; list each in "createsFiles" if this task creates it, or run the task that creates it first`,
            next: "pipeline-failuresExit.mmd::FAILURES_EXIT",
        };
    }
    return { ...packet, box: "INIT_SUBMODULES_RECURSIVELY", scriptSignal: SCRIPT_SIGNAL.CONTINUE, next: "DOCUMENT_GENERATION" };
}
```

Why `next` on the success path too: the hook uses `output.next` when the block has more than one successor. The block now has two.

Why `existsSync` and not `git cat-file`: the worktree is on disk with submodules populated. The disk is the truth here. This is the same check `loadPreparedTask` already makes later.

Run the same single test file again. All four tests must pass.

Do not edit `INIT_SUBMODULES_RECURSIVELY.template.json`. The block is `mutating`, so `tests/stepTemplates.test.ts` skips it, and `next` is routing metadata outside the data contract.
