# tackle-tasks pipeline exit audit

Every distinct way a `/tackle-tasks N` run can stop before the walk reaches
`pipeline-mergeSucceededExit.mmd::MERGE_SUCCEEDED_EXIT`. Columns:

`id | file:line | block/box | trigger condition | what the user sees | does resume (/tackle-tasks N again) recover it? | test coverage`

Sections: **A** = scripts/runStepHook.ts (the hook itself). **B** =
skills/tackle-tasks/tackle-tasks.workflow.js (the workflow driving the hook).
**C** = every block script under scripts/tackle-tasks/*/, grouped by diagram
folder. **D** = prompt/answer handling (scripts/tackle-tasks/shared/writeAgentAnswer.ts
and the blocks that consume an agent's answer).

**Total: 154 distinct exit rows** across sections A (18), B (5), D (3), and C
(128, across 6 diagram groups: preambleStatusCheck 19, failuresExit+reportOnlyExit
34, runFullSuite+rebase+commitMergeConflictFixIfNeeded+fixConflicts 27,
mergeSucceededExit 20, commitImplementationIfNeeded+fixImplementTaskTests+areTestsFlagged
20, lockSourceRepo+plan/review diagrams 32).

## Cross-cutting summary

**Silent — no report reaches the user at all:**
- **LOCK-4** (WAIT_FOR_LOCK⇄LOCK_SOURCE_REPO retry loop) — the only fully silent exit found in the whole pipeline. lockSourceRepo's own 15-minute wait cap sits *above* the harness's own ~10-minute hook execution ceiling, so the harness kills the hook process externally before its own `HAVE_15_MINUTES_PASSED_Q` check, `buildFailure`, or `uncaughtException` ever runs.

**Leave a lock or lease held (or a run falsely marked done/active):**
- **CMCF-4** (CONTINUE_REBASE) — `git rebase --continue` fails AND the fallback `--abort` also fails: the repo is left in a live, half-continued, half-aborted rebase, and the source lock stays held.
- **REBASE-3 / CMCF-5** — no box or shared helper on the rebase/continue path ever calls a lock-release function; every hard crash there strands the source-repo lock until a later successful pass or the 15-minute staleness window.
- **MSE-12** (CLEAN_UP_WORKTREES) — a crash after the worktree directory is physically deleted but before the function returns releases the source lock but never the worktree lease; resume then silently skips CLEAN_UP_WORKTREES forever.
- **FX-MTIF-selfcrash** (MARK_TASK_INACTIVE_FAILURE) — a crash here leaves `task.run.active` stuck `true` until resume gets back to this box.
- **LOCK-2** — a stranded `taskTools-source.lock.mutation-guard` file (from a mid-guard crash) blocks *every* future lock acquisition attempt for that repo until an operator manually inspects and removes it.
- **PRE-12** (RESET_WORKTREE) — a crash after deleting the old worktree but before recreating it can orphan a physical `.lease` file never recorded in tasks.json.

**Checkpoint left in a state resume cannot use:**
- **MSE-19 — the single most important structural finding of this audit.** `resumeRun.ts`'s row-3 resume path builds the ARCHIVE_TASK resume input from only 5 fields, which satisfies BUILD_CLOSURE_NOTE's contract but not ARCHIVE_TASK's (missing `closureNote`). Once a run reaches `state.active===false` with no surviving worktree after an ARCHIVE_TASK crash, `/tackle-tasks N` can **never again** complete archival — every resume reproduces the identical contract-mismatch failure forever. `resumeRun.test.ts` asserts the broken payload as the *expected* value, so nothing catches it.
- **PRE-12** — RESET_WORKTREE deletes `plans/checkpoint.json` along with the old worktree; resume falls back to ending the run as "agent-failed" instead of continuing it.
- **failuresExit chain (C.2)** — once `inFailureChain=true`, every checkpoint write is suppressed for the rest of that chain; if the worktree itself vanishes mid-chain, `findResumeEntry` returns null with no error, and the task is never picked up again.

**No test coverage at all, for a real crash path:**
- **B1-B5** (tackle-tasks.workflow.js) — none of the workflow's 5 failure-return branches is asserted by any test under `tests/`.
- **A1, A16, A17, A18** (runStepHook.ts's plain `throw`s and resetTask.ts) — `resetTask.test.ts` has exactly one test, the happy path; none of resetTask's 7 throw sites are tested.
- **D1/D2** (writeAgentAnswer.ts validation throws) and the "answer silently ignored" boxes — **MISC-26**, **MISC-28**, and COMMIT_MERGE_CONFLICT_FIX_IF_NEEDED — none read `message`/`additionalData` at all, so a missing/malformed prompt answer is neither validated nor reported.
- **IMPL-6** (RUN_TASK_TESTS) — `spawnSync` has no `timeout` option in `taskTestsRunner.ts`; a hung `npm test` blocks until the hook's outer 300s kill, and the orphaned test-runner grandchild process isn't guaranteed to die with it, risking a second concurrent suite run on resume.
- **FX-\*-selfcrash rows generally** — every "this failuresExit-chain box itself hard-crashes" scenario has zero test coverage; only the idempotent-replay ("runs twice") case is tested for each box.

### C.2 pipeline-failuresExit.mmd + pipeline-reportOnlyExit.mmd (scripts/tackle-tasks/failuresExit/, scripts/tackle-tasks/reportOnlyExit/)

This is the tail every other pipeline failure routes into, to release the source-repo lock and worktree lease, mark the task inactive, and write the exit report. `inFailureChain=true` is set the moment the box before FAILURES_EXIT chooses it as `next` (runStepHook.ts:385-407); from that point on **every checkpoint write is suppressed for the rest of the chain** (the `!inFailureChain` gate at runStepHook.ts:317), so a crash anywhere inside this chain leaves `checkpoint.json` pointing at the **pre-chain** box, with `state:"failed"` and that box's own `exitType`/`exitNote`/`sourceLockHeld` frozen at chain-entry time.
