Level 2

Plan is a review loop

The planner writes, a reviewer (codex or claude) judges, feedback is applied, repeat. The cap is MAX_REVIEW_ROUNDS = 3. The loop has no terminal branch: when the cap runs out on a rejected verdict, the code falls out of the while and returns status: "planned" anyway. Run B spent about 268K tokens on three rejected plans, then implemented the third one.

Level 3

Bootstrap and the per-task worktree

Worktrees are not created per task after planning — they are created inside prepare, before any task workflow launches. prepareTasks.ts makes one worktree per task group under /tmp/taskTools-wt/<repo>/task-N, takes a lease on it, and materializes one copy of the workflow script per task. Run B called prepare twice; the skill body only tells the orchestrator to call it once, and nothing consumed the first result.

Level 4

Merge is a queue, and rebase-test guards it

Between implement and merge sit two things the level-1 sketch hides: a human approval gate in the main conversation, and a rebase-test stage that rebases every layer onto the source branch and runs the full suite. The orchestrator never decides a launch itself — it asks nextSchedulerAction every time. Run B died inside rebase-test and never reached the gate's merge side.

Level 5

Full sequence with cleanup

Merge returns one of three success shapes. Only cleanup-incomplete leaves work behind, and that work is a separate cleanup-only stage launch — it never re-merges or re-closes. In run B, nothing past rebase-test executed, so the worktree, its branch, and its lease were all left standing.

Note

Two corrections to the level plan

Worktree setup is not level 3

It belongs to bootstrap's prepare mode and happens once, for all tasks, before any plan runs. It is not a per-task step wrapped around the plan loop.

Two phases are missing entirely

The human approval gate and the rebase-test stage both sit between implement and merge. Rebase-test is where run B actually died, so the map is not useful without it.
